# 踩坑大全（平台特性 + 可迁移经验）

> 每条都付出过真实代价。适用于：国科/海思方案的运营商 Android 盒子，部分经验通用于所有 Android。

## A. root 与提权

### A1. su 有调用方白名单，文件权限位救不了
- 现象：`/system/xbin/su` 为 `-rwsr-x--- root shell`，应用 exec 报 `IOException error=13 (EACCES)`。
- 误修：`chmod 4755` 后文件可执行了，但 su 输出 **"su: not allowed"** —— su 二进制内部按调用方
  uid/包名白名单放行（本机只放 shell/root 组）。
- 结论：**别指望让应用走 su**。出路：① SELinux Permissive 下直接 SystemProperties（本项目用法）；
  ② 换成应用可用的 su（如 Magisk 授权）——需要 patch boot，风险自评。

### A2. `su` 的语法陷阱
本机 su 是 busybox 风格：`su 0 <cmd>` ✅、`su -c <cmd>` ❌（报 invalid uid/gid '-c'）。
写跨机脚本时两种都试（见 `src/tvfix/.../RootShell.java` 的 attempts 数组）。

### A3. SELinux Permissive 是普通应用的绿灯（本项目的根基）
`getenforce` = Permissive 时，avc 拒绝**只审计不执行**：
- 应用可以 `SystemProperties.set("service.adb.tcp.port","5555")` ✅
- 应用可以 `SystemProperties.set("ctl.restart","adbd")` ✅（init 收到后真的会重启服务！）
- 应用可以执行任意系统二进制（如 busybox）
先 `getenforce` 看一眼再设计提权方案，能省掉一整条 root 链路。

## B. 开机自启

### B1. 刚装完的应用收不到 BOOT_COMPLETED（stopped 状态）
`pm install` 之后应用处于 stopped 状态，**所有广播都被丢弃**（含 BOOT_COMPLETED），
直到它被打开过一次。`pm install -r` 更新是否保留"非 stopped"状态不可依赖——
**装完就 `am start` 一次**，一了百了。

### B2. 该平台 init 不解析 /system/etc/init/ 下新增的 .rc
ROM 自带的 rc（audioserver.rc 等）在那儿工作正常，但**运行期新增的 rc 文件**：
- 开机不解析（实测 trigger 不触发）；
- 开机后再改文件更不会重读（init 只在启动时解析）。
固化"开机做某事"别押注这条路。可靠的是：应用 BOOT_COMPLETED 接收器 + 应用打开过一次。

### B3. build.prop 属性单独不够
`service.adb.tcp.port=5555` 写进 build.prop 后，若 adbd 服务**根本没有被启动**
（本机 `persist.sys.usb.config=none`，开机不拉 adbd），属性写得再对也没人读。
属性负责"监听哪个端口"，**还得有人负责把 adbd 启动起来**（ctl.restart / adb_enabled 链路）。

### B4. 永远不要在 adb shell 会话里 `stop adbd`
adbd 一死，挂在它下面的 shell/su 全部陪葬，`start adbd` 永远执行不到，直接失联。
要重启 adbd：从应用进程里做（TvFix 的做法），或者 `nohup sh -c 'stop adbd; start adbd' &`。

## C. 默认桌面（HOME）

### C1. preferred activity 记录可能被系统持续作废
`cmd package set-home-activity` 返回 Success ≠ 生效。本机日志：
`PackageManager: Result set changed, dropping preferred activity for Intent {HOME}`，
`resolve-activity` 永远显示 ResolverActivity。
**但真实 HOME 键行为不受影响**（候选排序仍在工作）——别被探测命令误导，要实测按键。
固化方案用 `intent-filter android:priority`（包扫描期属性，不依赖运行时记录）。

### C2. 替身启动器：比反编译更干净的去登录方式
若运营商 HOME 只有一个入口 Activity（用 `aapt dump xmltree` 确认），可自建**同包名同类名**
的迷你 APK 原位替换（备份原版 + 删 oat 目录防 odex 校验），登录代码物理消失。
比 apktool 改 smali 重打包省掉一整层工具链，签名自由。

### C3. 系统应用原位替换注意事项
- 替换前备份到 /data/local/tmp（/system 是 ro，先 remount rw）；
- **删掉 APK 同目录的 oat/**（旧 odex 与新 APK 的 dex 校验和不匹配）；
- chmod 644 + chown 0.0 + restorecon + sync；
- 重启后 PMS 重新扫描（签名变化对"被替换的系统应用"是合法的全新扫描）。

## D. 开发与部署

### D1. 这台机器 `adb install`（streamed）是坏的
报 `failed to stat`。用 `adb push` 到 `/data/local/tmp` + 盒端 `pm install -r` 代替。

### B/D2. shell 读不了 /system/build.prop（Permission denied）
排查 build.prop 内容要用 `su 0 grep`。别被 shell 的 ENOENT/EACCES 假象骗了。

### D3. 从卡刷包提取 APK 的完整链路
`update.zip` → `system.new.dat.br` →(python brotli)→ `system.new.dat`
→(sdat2img + transfer.list)→ ext4 raw image →(python `ext4` 库)→ 按路径取文件。
坑：ext4 dirent 的 name 字段带垃圾填充字节，必须清洗后再查 inode（脚本已处理）。

### D4. 无 Gradle 快速构建 APK
aapt2 link（仅清单无资源）→ javac --release 8 → d8 → zip 塞 classes.dex → zipalign → apksigner。
5 个命令构建一个 TV 应用，CI 或应急都好用（见 `scripts/build_apk.sh`）。

### D5. 诊断要打日志文件
应用的 shell 执行结果 UI 上转瞬即逝（tv 盒子连截屏都麻烦）。让接收器把每步输出写
`/data/data/<pkg>/files/boot.log` + 脚本侧写 `/data/local/tmp/*.log`，adb 一拉就真相大白。
v3 加了日志后，"su: not allowed" 一行就推翻了之前所有假设。

## E. 网络与 DNS（运营商盒子高发）

### E1. 运营商下发的 DNS 可能全是哑的
现象：ping IP 通、所有域名解析失败，"网络特别差"。诊断：`ping -c1 www.baidu.com` vs `ping -c1 223.5.5.5`。
修复（root）：`ndc resolver setnetdns <netId> "" 223.5.5.5 119.29.29.29`（netId 从
`dumpsys connectivity` 的 `network{100}` 读）。
坑：netd 配置**每次开机被框架重置**；ndc 对应用的拒绝不是 SELinux 而是
**/dev/socket/netd 的 unix socket 属组**（chown/chmod 层，permissive 也绕不开）。

### E2. 这台平台 init 对 rc 的真实规则（血泪三连测）
- 新增 /system/etc/init/xxx.rc：**不解析**；
- 向已解析的 rc（atrace.rc / audioserver.rc）追加 `on property:` 触发器：**不执行**；
- 向已解析的 rc 追加 **service 定义 + class main**：**生效！**（init 的 class_start main 自动拉起）
结论：在这类盒子上做开机常驻 root 任务，用"service + class main"形态，别用属性触发器。

### E3. 国内的下载通道打法
- GitHub release 大文件直连必断流 → 前缀代理 `https://ghfast.top/` 或 `https://gh-proxy.com/`（后者更稳）；
- 断点续传 `curl -C -` 循环直到 unzip 校验通过（Kodi 80MB 磨了 10+ 轮）；
- 当贝系直链（webapk.dangbei.net）必须带**移动端 UA**，否则返回反爬 HTML；
- download.mozilla.org 的 `?product=fennec-latest&os=android` 可直连（配 -C -）；
- 盒子上 curl/wget 都没有时，Mac 下载 + adb push 是万能兜底。

## F. root 与提权（结论篇）

### F1. 应用 root 是系统级死路（Android 8+）
三道锁，逐个破解后仍会撞到最后一道：
1. su 文件权限 4750 root:shell → `chmod 4755`（**必须 chown 先、chmod 后，chown 会清 S_ISUID 位！**）；
2. su 二进制调用方白名单（"not allowed"）→ capstone 反汇编，NOP 掉拒绝块（scripts/patch_su_whitelist.py）；
3. **zygote seccomp 过滤器禁止应用进程 setuid/setgid 系统调用** → 无解（内核级）。
⇒ 应用要 root：root 守护进程 + socket 通信（Magisk 的本质）。交互式 root 用 `su 0`（shell/adb 上下文）。

### F2. `adb root` 是 debuggable 机器的最后通道
ro.debuggable=1 的机器，`adb root` 让 adbd 以 uid 0 重启——**不依赖 su**。
su 被搞坏时（如部署失误清了 setuid 位），它是 10 秒级的救命通道。修复后记得 `adb unroot` 不必须。

### F3. su 降权会保留调用方附加组
`su 10037 <cmd>`（盒子 su 语法：`su <uid> <cmd>`）把 uid 降成应用身份时**保留 shell 的全部附加组**
（含 inet 3003）——所以从 shell 用 su 降权跑网络程序是通的，而应用自己 exec 反而不通。
这个不对称性可以用来做"半降权"运维。

### E4. 当贝市场"认为设备是手机"的根源与修法
现象：当贝市场拒绝安装应用，判定设备非 TV。根源：盒子 `ro.build.characteristics=default`
（应为 tv），国内 TV 应用常用 `getprop ro.build.characteristics` 判机。
修复（root，一行）：`sed -i s/ro.build.characteristics=default/tv/ /system/build.prop` + 重启。
注意 `pm list features` 里 television/leanback 本来就在——所以别信 features，要查 characteristics。

### E5. 沙发管家已死
shafa.com 直链（app.shafa.com/shafa.apk）返回 HTML 反爬页——沙发管家已停运。
TV 应用管理/商店的活路：当贝市场（配合 E4 修正）或纯本地安装（文件管理器 + U盘）。

### E6. TV 文件管理器推荐（开源）
Material Files（me.zhanghai.android.files）：开源、带 leanback 横幅、支持局域网/USB，
GitHub zhanghai/MaterialFiles releases，经 ghfast 代理下载。

### F4. init service 开机自启的标准姿势（对 E2 的落地模板）
```
service 名字 /system/bin/sh /system/bin/你的脚本.sh
    class main
    user root
    oneshot
    seclabel u:r:su:s0
```
追加到已被解析的 rc（本机用 audioserver.rc），`class main` 让 init 在 class_start 阶段自动拉起，
root 身份 + su domain，完全绕开属性触发器不解析的坑。实例：scripts/install_dns_service.sh
（DNS 守护 tvfixdns + Termux sshd 自启 tvfixsshd 两个服务）。

### F5. 应用 su 的死因是 zygote seccomp，不是 su
补丁 su 白名单后：shell/adb 上下文全通；应用上下文依然 `setgid failed: EPERM`——
Android 8+ zygote 对 fork 出的应用进程装了 seccomp 过滤器，**setuid/setgid 系统调用直接 EPERM**。
setuid 二进制对应用是内核级死路，Magisk 的本质是用 init 级 root 守护进程 + socket 通信绕开它。

### F6. chown 会清 setuid 位
部署 setuid 二进制的正确顺序：`cp → chown → chmod 4755`。顺序反了 setuid 位被静默剥掉，
表现为 `su: setgid failed: Operation not permitted`。另记：ro.debuggable=1 的机器
`adb root` 是 su 失效时的 10 秒救命通道。
