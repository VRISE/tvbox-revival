## 阶段一：侦察（10 分钟定全局）

```bash
adb connect <盒子IP>:5555
adb shell getprop ro.product.model          # M401H_CMIOT20_ZJ42
```

## 阶段二：从卡刷包提取当贝 APK（不联网下载，用本地资源）

用户 Downloads 里已有该机型"当贝桌面免拆卡刷包"（update.zip，520MB）。
卡刷包内 `system.new.dat.br`（brotli 压缩的动态分区镜像）+ `system.transfer.list`：

```bash
pip install brotli ext4        # ext4: 纯 python 只读 ext4 实现
unzip update.zip system.new.dat.br system.transfer.list
python3 -c "import brotli; open('system.new.dat','wb').write(brotli.decompress(open('system.new.dat.br','rb').read()))"
python3 sdat2img.py system.transfer.list system.new.dat system.img   # 854MB ext4
```

然后用 python `ext4` 库从镜像里拎出 `/system/app/launcher/Launcher.apk`
（com.dangbei.tvlauncher）。注意：ext4 dirent 名字里带垃圾填充字节，要清洗后再当路径查 inode。
（完整脚本见 `scripts/extract_apk_from_rom.py`）

## 阶段五：SkyLoader 替身（主人点名的终极方案）

主人问："为啥不能改掉它的验证功能，默认就能进系统？"——答案是能，而且比想象的干净：

```
aapt dump xmltree SkyLoaderA9_orig.apk AndroidManifest.xml
```

## 阶段六：ADB 固化长跑（事故二、三）

TvFix 开机自启 ADB 的闭环，前后改了 4 版：

### 事故二：装完没打开过 = 收不到开机广播
TvFix 装完从未启动过 → 处于 Android "stopped 状态" → **BOOT_COMPLETED 不投递**。
重启后 TvFix 接收器根本没跑，ADB 3 分半没起来，主人只能又手动开了一次调试。
**教训：pm install 之后必须 `am start` 打开一次。**

### 事故三：在 adb shell 里 `stop adbd` 自杀
为了验证脚本，直接在 adb 会话里跑 `su 0 sh -c 'stop adbd; start adbd'`——
`stop` 杀掉 adbd 的同时把挂在它下面的 shell/su 一起带走了，`start adbd` 永远执行不到，当场失联。
**教训：这类命令只能从"不挂在 adbd 下"的上下文执行（应用内、或 nohup）。**
讽刺的是这正是 TvFix 应用内执行的天然优势——它的进程挂在 app 下，怎么重启 adbd 都死不了自己。

### 真相：su 的调用方白名单
chmod 4755 修好文件权限后（原本 4750 root:shell，应用 exec 报 EACCES error=13），
TvFix 日志显示 su 能执行了但输出 **"su: not allowed"** —— su 二进制自带调用方白名单，
应用身份被硬拒。此路不通。

### 破局：SELinux Permissive 下应用可以直接操作系统属性
```java
SystemProperties.set("service.adb.tcp.port", "5555");
SystemProperties.set("persist.adb.tcp.port", "5555");
SystemProperties.set("ctl.restart", "adbd");   // init 真的会重启 adbd！
```
实测 adbd PID 变化、端口生效。**全程无 su、无 root 需求。**
配合 privapp-permissions 白名单写 `adb_enabled=1`（标准调试链路，双保险）。

### 应用安装（全部验证）

安装方式统一：`adb push` 到 /data/local/tmp + 盒端 `pm install -r`（该机 adb install 流式通道是坏的）。

### 网络真相：DNS 从来就是坏的
"网络特别差"不是折腾出来的——运营商 DHCP 下发的 DNS（211.140.13.188 / 211.140.188.188 / 192.168.5.1）
**全部无法解析**，盒子从刷机起就只能纯 IP 直连。修复：`su 0 ndc resolver setnetdns 100 "" 223.5.5.5 119.29.29.29`。
难点：netd 的 DNS 配置每次开机被框架重置；**这台 init 不解析任何运行期新增/追加的 rc 触发器**
（adbfix.rc / atrace.rc 追加 / audioserver.rc 追加，三种全试全灭）。

### 最终解法：service + class main（不走属性触发器！）
向**已确认被解析**的 `/system/etc/init/audioserver.rc` 追加 **service 定义**（不是 on 触发器）：

```
service tvfixdns /system/bin/sh /system/bin/dnsfixd.sh
    class main
    user root
    oneshot
    seclabel u:r:su:s0
```

`class main` 的服务在 init 的 `class_start main` 阶段自动启动——不需要任何属性触发器！
dnsfixd.sh 以 root 常驻循环（45 秒一次 ndc），`getprop init.svc.tvfixdns = running` 确认。
配合 /system/etc/hosts 钉扎 ustc 镜像 IP，Termux 的 apt 也通了。
（一次性解法留给用户：设置里把以太网改静态 DNS 223.5.5.5，框架级持久。）

### su 补丁实验（结论：应用 root 是系统级死路）
- su 白名单 {0, 2000} 位于 0xb5e `cmp r0,#0x7d0` + 0xb64 拒绝块；
- capstone 反汇编定位后 NOP 掉 12 字节拒绝块（scripts/patch_su_whitelist.py）；
- shell 侧一切正常；**应用侧依然 `setgid failed: EPERM`——Android 8+ zygote seccomp 过滤器
  在系统层面禁止应用进程调用 setuid/setgid**，setuid 二进制对应用是死路（Magisk 的本质就是
  绕开它：root 守护进程 + socket 通信）。应用要 root 只能走守护进程方案。
- 事故与自救：部署时 `chown 0.0` 把 chmod 4755 的 setuid 位清掉了（chown 会清 S_ISUID！），
  su 全线失效；靠 **`adb root`**（ro.debuggable=1）10 秒救回。教训：**先 chown 后 chmod**；
  ro.debuggable 的机器永远有 adb root 这条最后通道。
- 应用要 root 只能 root 守护进程方案（本机未做，Magisk 路线需要 patch boot，风险高）。

### Termux = Linux 服务器
- 装完必须打开一次（bootstrap 自解压 + 解除 stopped 状态）；
- apt 拒绝 root 身份 → 用 `su 10037`（盒子 su 降权会**保留 shell 的全部附加组**，含 inet 3003，
  所以网络可用）+ 完整 env（HOME/LD_LIBRARY_PATH/PATH/TMPDIR）；
- sshd 8022 免密 key 已配，Mac `ssh -p 8022 <IP>` 即入（armv7l，433 个命令）；
- 自启：Termux:Boot（~/.termux/boot/start-sshd.sh）+ ~/.bashrc 守卫式兜底。
